# Experiment results — 2026-11-12

The skill did not improve factual verdict accuracy on this small development
suite: both arms passed 3/3 tasks. Its initial reports were more complete about
operational rollout, but 2.46× longer. The actionable improvement was to constrain
default output length, not to claim a quality gain from an already saturated test.

## Execution and provenance

- Dokimi: `3b61dd01fc238d4620644681ca8a88994becaa5c` (0.2.0).
- Initial skill: PR #41 commit `13482741042daf225d15244d484571e9043acf9c`.
- Six fresh agent sessions: three tasks × baseline/skill, one run per cell.
  Same inherited parent configuration; exact model ID/tokens unavailable.
- Answers were generated by collaboration agents and then scored by Dokimi,
  not generated by a Dokimi model backend. External LLM API credentials were not
  configured; Claude CLI was absent and the Codex CLI initialization failed with
  a read-only filesystem error. Novelty analysis was estimated, not measured.
- Local task sources were inspected; flow and numeric agents executed their
  local tests. No production repository was changed, no proof service received
  source, and no infrastructure or merge protection was modified.

All 13 structured decisions match their frozen expectations, but they belong to
three task units. Do not report them as 13 independent experiments or infer
statistical significance. Existing flow tests report 3 pass/1 fail in both arms;
helper computation is independently correct. Both numeric runs report two tests
passing and oracle success at four sizes; timing differs by environment/noise.

Manual report review found both arms correctly diagnosed the core defects and
limitations. Initial skill reports consistently named evidence levels, owner roles,
estimated runtime budgets, staged rollout and rollback. Baseline reports already
offered useful fixes, but less consistently specified those operational fields.
This observation is a non-blinded review by the skill author, not an independently
calibrated quality score. It does not prove better implementation outcomes.

## Fix and targeted retest

The skill now defaults to 400–800 words and uses full category/ledger tables only
when requested or necessary. It still inspects all categories and preserves cited
findings, limitations and actionable pilots. Its description now states “Use when”.

A fresh compatibility-only retest produced 786 words versus the previous 1,854
(58% shorter, rounded), retaining all five correct verdicts, scoped claims,
negative controls, owners, budgets and rollout/rollback. This is a same-case
post-tuning development retest, not an independent holdout or causal estimate.
Other tasks were not rerun with the shortened-report instructions.

## Dokimi measurements

- **Catalog:** all three skills load; no strict spec errors. Initially each had
  two warnings. The new skill's `description-no-when` warning was fixed. Its
  remaining `frontmatter-unknown-key` warning concerns intentional repository
  catalog metadata required by the repo's own validators; it was not suppressed
  or removed. The two older skills retain both warnings.
- **Lexical routing:** 12 requests, 10 scored, 8 correct picks, one wrong sibling
  pick and one no-match. Two queries were unscored. For the assessment skill,
  3/3 scored queries selected it, with its Russian query unscored. Results were
  unchanged after the description edit. This is a lexical floor, not LLM routing
  accuracy or multilingual capability evidence.
- **Reference scorer controls:** 22 healthy answers accepted; 19 corrupted answers
  scored and rejected; three empty answers recorded as errors. No corrupted
  response passed. The exact JSON grader does not evaluate prose quality.
- **Repository inspection:** ran on `napetrov/skills`, `intel/dokimi` and the
  supplied Prove2me workspace. Static results identify declared check surfaces;
  they do not establish execution or branch enforcement.
- **Prove2me:** pinned at `9140932a4c92dfb87466da9014f47dc772584f69`.
  Its skill loads, with a body-size warning (~5,137 tokens estimated by characters).
  Generic repo inspection reports missing tests/root instructions, although the
  tree contains `SmokeTest.lean` and `SKILL.md`. Treat these as detector/applicability
  limits for a Lean workspace, not proof of missing validation or documentation.
  We did not compile its Lean project or test server-side proof guarantees.
- **Novelty:** estimate-only triage run with resources: 252 spans, estimated 6,778
  tokens and 112 model calls at the default settings. No knowledge-novelty,
  redundancy, contradiction or model-based routing result was measured. The
  estimate's list-price projection is not incurred spend or a budget commitment.

## Exploratory real-repository assessment

A fresh agent applied the revised skill to a bounded scope of the real Dokimi
repository (reference grading, static checks and CI linkage). Its 657-word
[report](records/2026-11-12/outputs/real-dokimi/report.md) cites implementation and
tests and proposes two concrete pilots: visible partial-grading completeness and
inspection receipts for skipped/static-unchecked files. The parent inspected the
relevant source and tests to confirm these are existing semantics/visibility risks,
not newly demonstrated product defects. This was read-only and unscored; no claim
of whole-repository audit completeness or production execution is made.

A separate minimal CLI canary confirmed the partial-grade behavior: one exact
check passes, a judge check is not run under `--no-judge`, and Dokimi reports
`pass_rate: 1.0` **with `judge_unscored: 1`**. This is intentionally partial scoring,
not proof that all criteria passed. The canary inputs are stored beside the
summary; use `eval score reference --no-judge` to reproduce. Consumers should
read completeness counters with pass rate. The compatibility compact-output
retest was also rescored through Dokimi and passed 1/1.
